# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project — AI & ML Certification Program, E&ICT Academy, IIT Roorkee.

One connected pipeline that answers three questions for the regional operations head:

1. **How long will a parcel take?** — delivery-hours regression (Part B).
2. **Which parcels will miss their promise?** — delay classifier plus an alert threshold set by the operations rule (Part C).
3. **Which hubs need which playbook?** — K-Means hub segments checked against the Tier labels (Part D).

Part A's cleaning and feature functions (`src/shipment_prep.py`) feed every later Part and the final scoring script, so training and prediction share one preprocessing path.

> All data is synthetic and produced by `generate_data.py`. No real Delhivery records are used.

## How to run

From a fresh clone, in the repository root (Python 3.12 was used):

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py       # data/modelling_table.csv + outputs/part_a_*.csv
python part_b_regression.py      # outputs/part_b_*.csv
python part_c_classification.py  # outputs/part_c_*.csv
python part_d_segments.py        # outputs/hub_profile.csv, hub_segments.csv, segment_profile.csv, ...
python package_model.py          # models/* + outputs/part_d_reload_check.csv
python predict_delay.py          # outputs/new_shipment_actions.csv
```

Run every script from the repository root, in this order; each step reads only files written by the steps before it.

**About the model pickle:** `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (scikit-learn 1.5.2); when installed versions differ, re-run `package_model.py` instead of loading the committed pickle. `predict_delay.py` is deterministic — running it twice produces byte-identical output.

Every CSV is written with `index=False` and decimals rounded to 4 places (except `part_a_correlations.csv`, whose row labels are kept as the first column `column`, and `train_scaled_max_abs_mean` in `part_b_checks.csv`, which is written in scientific notation so the ~1e-15 value stays visible instead of rounding to 0).

## Data findings

Source files: `outputs/part_a_checks.csv`, `outputs/part_a_delay_by_group.csv`, `outputs/part_a_correlations.csv`.

**Cleaning summary.** The raw export had 1,224 rows; 24 exact duplicates were removed, leaving 1,200 shipments (all 1,200 survived the hub merge). Before filling there were 36 missing `distance_km`, 24 missing `parcel_weight_kg` plus 5 scanner-fault sentinel weights (999 kg), 12 missing `declared_value` and 18 missing `payment_mode`. `service_type` had 12 spellings, reduced to 3 after strip + title case. Gaps were filled with medians: distance 314.95 km, weight 1.83 kg, declared value INR 1,121.50. After cleaning there are 0 missing cells in the 17 features plus target. 278 parcels are delayed (delay rate 0.2317). Delivery hours have Q1 = 43.255 and Q3 = 72.5625; the 1.5 × IQR bounds are −0.7063 to 116.5238, with 1 outlier.

1. **Service type.** Express is delayed most often: 119 of 243 parcels, a delay rate of **0.4897** — almost half. Standard is at 0.2056 and Economy at 0.0857. Express has the tightest promise (36 h), so it has the least slack to absorb sale-week and rain effects.
2. **Hub tier.** Delay rate climbs steeply with tier: Tier 1 **0.0400** (16 of 400), Tier 2 **0.2150** (86 of 400), Tier 3 **0.4400** (176 of 400). Tier 3 hubs miss promises 11 times as often as Tier 1.
3. **Distance band.** Delay rate rises with lane distance: 0-200 km **0.0219**, 201-400 km **0.1368**, 401-600 km **0.4364**, 601+ km **0.8523** (75 of 88 parcels). Above 600 km a parcel is more likely late than on time.
4. **Strongest correlations with `delivery_hours`** (ranked by absolute value, `delivery_hours` itself excluded): `promised_hours` **0.8372**, `distance_km` **0.4013**, `n_stops` **0.3247** — all positive. `promised_hours` is high because it encodes service type, which sets the base transit time; distance and route stops then add hours. (For the delay flag, corr(`is_delayed`, `distance_km`) = 0.5455.)
5. **Why log-transform declared value.** The filled `declared_value_inr` is right-skewed: mean INR 1,533.05 versus median INR 1,121.50. After the natural log the mean (7.0277) and median (7.0224) almost coincide, so `log_declared_value` is roughly symmetric and a few expensive parcels no longer dominate scale-sensitive models.

## Model results (regression)

Source files: `outputs/part_b_checks.csv`, `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv`.

- **Split and leakage check.** 840 / 180 / 180 rows (train / validation / test). The StandardScaler was fitted on training rows only: the largest absolute column mean of the scaled training rows is 1.4391e-15 (zero), while the scaled test rows reach 0.2187 — proof the scaler never saw the test rows.
- **Baseline.** Predicting the training mean for every parcel gives validation R² **−0.0212** (RMSE 18.8552 h). An R² at or below zero means the model explains none of the variation; any useful model must beat this.
- **Validation winner.** Linear regression has the lowest validation RMSE, **4.8912 hours** (R² 0.9313), just ahead of gradient boosting (RMSE 4.9165, R² 0.9306). Random forest reaches R² 0.9129 and the depth-6 decision tree 0.8867. The underlying process is mostly additive, which suits a linear model.
- **Tree depth (bias vs variance).** Depths 1–3 are **high-bias**: both errors are high and close (depth 1: train 11.6334, val 12.1324, gap 0.50). Depth 6 is the sweet spot with the lowest val RMSE **6.2796**. Depths 8, 12 and unlimited are **high-variance**: train RMSE keeps falling (3.3360 → 1.3613 → 0.0000) while val RMSE rises again (6.7901 → 7.3540 → 7.8368); the unlimited tree memorises the training rows with a gap of 7.84 hours.
- **Learning rate.** 0.1 is best (val R² 0.9306, RMSE 4.9165). 0.01 is **too slow**: with only 100 trees each step is so small the model is still underfitting (R² 0.7127). 1.0 **overshoots**: each tree corrects the full residual, so it overfits noise and oscillates (R² 0.8429).
- **Cross-validation.** 5-fold CV (one shared `KFold(5, shuffle=True, random_state=42)`) on the 1,020 training + validation rows gives linear regression mean R² **0.9261** (std 0.0048) and gradient boosting **0.9353** (std 0.0045). The CV ranking disagrees with the single validation split: on validation the two models differ by only 0.025 hours of RMSE, while CV, averaged over five folds and 1,020 rows, favours gradient boosting by about 0.009 R².
- **Final model and what I would ship.** Following the brief's rule, the final model is linear regression (lowest validation RMSE), scored once on test: RMSE **4.5235 h**, R² **0.9493**. For production I would ship **gradient boosting**: its CV mean R² is higher with an equally small spread, and five folds over 1,020 rows are stronger evidence than one 180-row validation split. Linear regression stays a good, transparent fallback since the gap between the two is small.

## Model results (classification)

Source files: `outputs/part_c_models.csv`, `part_c_feature_scores.csv`, `part_c_selectk.csv`, `part_c_tuning.csv`, `part_c_thresholds.csv`, `part_c_final_test.csv`, `part_c_final_config.csv`.

- **Stratified split.** 840 / 180 / 180 rows with 195 / 42 / 41 delayed parcels.
- **Blind baseline.** Predicting "on time" for everyone gives validation accuracy **0.7667** (TN 138, FP 0, FN 42, TP 0) but recall 0 — it catches none of the 42 delayed parcels, which is exactly what ops needs. Accuracy alone hides that, because 77% of parcels are on time anyway.
- **Trained models (threshold 0.5, validation).** Logistic regression F1 **0.8046** (accuracy 0.9056); best decision tree depth 6, F1 **0.7470** (accuracy 0.8833); default random forest F1 **0.8000** (accuracy 0.9111). All beat the blind accuracy.
- **Noise columns.** The five bookkeeping columns together take **0.2252** of the 17-column forest's importance — the forest spends almost a quarter of its splits on random numbers. By F-score all five fall outside the top 7 (ranks 8, 12, 14, 16, 17; highest F-score 4.5847 for `label_print_batch`). The top 7 by F-score are `distance_km` (389.2131), `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag` (36.7281).
- **What the k table shows.** Validation F1 by k: 5 → 0.6988, **7 → 0.8333**, 10 → 0.8140, 12 → 0.8049, 17 → 0.8000. Five columns drop real signal (rain and sale-week), seven is best, and adding more columns (which brings in noise) slowly lowers F1.
- **Tuning.** On the 7 selected columns: grid search (27 candidates × 5 folds = 135 fits) best CV accuracy **0.8952** with `max_depth=6, min_samples_leaf=1, n_estimators=100`, val F1 0.7750; randomized search (9 × 5 = 45 fits) best CV accuracy 0.8905, val F1 0.7901; the untuned forest on the same 7 columns has val F1 **0.8333**. Tuning did **not** beat the untuned forest on validation. Searches optimise CV accuracy on the training rows, not F1, and on a 180-row validation set with 42 delayed parcels one or two parcels change F1 by several points — so these differences are within noise. The final configuration is the untuned forest (`chosen_from = default_forest_same_7_features`: k=7, 100 trees, unlimited depth, min_samples_leaf 1).
- **Alert threshold.** Rule: highest threshold whose validation recall is at least 0.80. Recall is 0.8333 at 0.5 and drops to 0.7619 at 0.6, so the threshold is **0.5**. At 0.5 the validation precision is 0.7955 (35 true alerts, 9 unnecessary calls) and recall 0.8333 (7 of 42 delayed parcels missed). Going to 0.6 would raise precision to 0.8889 but miss 10 delayed parcels; going down to 0.3 would catch 39 but make 17 unnecessary calls. Since a missed delay costs more than a call, recall is held at 0.80 or more.
- **Single test evaluation (threshold 0.5).** TN 125, FP 14, FN 10, TP 31: precision **0.6889**, recall **0.7561**, F1 **0.7209**, accuracy 0.8667. Test recall (0.7561) is below validation recall (0.8333): honestly, the 0.80 recall target was met on validation but not on test. With only 41 delayed test parcels, one parcel moves recall by about 0.024, so the 0.077 gap is about three parcels — expected variation, but it means the 0.80 target should be monitored in production rather than assumed.

## Operations recommendation

Source files: `outputs/hub_segments.csv`, `segment_profile.csv`, `tier_vs_segment_mismatch.csv`, `part_d_separation.csv`, `part_c_final_test.csv`, `new_shipment_actions.csv`.

**Segments.** K-Means (K = 3) on hub-level delivery hours, delay rate, distance and stops gives:

| Segment | Hubs | Mean delivery hours | Delay rate | Mean distance (km) | Mean stops |
|---|---|---|---|---|---|
| Standard | 7 | 47.2396 | 0.0257 | 188.9296 | 55.3686 |
| Watch | 8 | 56.8137 | 0.1550 | 314.1762 | 70.7175 |
| Escalate | 9 | 64.6504 | 0.4600 | 470.4757 | 84.3444 |

**Escalate hubs (delay rate):** HUB13 Nagpur 0.46, HUB15 Kochi 0.36, HUB17 Patna 0.46, HUB18 Ranchi 0.38, HUB19 Guwahati 0.62, HUB20 Raipur 0.48, HUB21 Bhubaneswar 0.40, HUB23 Siliguri 0.44, HUB24 Agartala 0.54. Guwahati and Agartala are the worst and should be first in line for hub-manager reviews.

**Hubs whose tier label is misleading** (`tier_vs_segment_mismatch.csv`):

- **HUB07 Kolkata** — Tier 1, behaves like **Watch** (delay rate 0.14, distance 304.736 km). Do not plan it as a metro hub.
- **HUB13 Nagpur** — Tier 2, behaves like **Escalate** (delay rate 0.46, 473.320 km lanes).
- **HUB15 Kochi** — Tier 2, behaves like **Escalate** (delay rate 0.36, 466.514 km lanes).
- **HUB22 Dehradun** — Tier 3, behaves like **Watch** (delay rate 0.20), better than its label.

So the tier label should not drive playbooks on its own: it is right for 20 of 24 hubs, but staffing, escalation and customer-communication rules should follow the measured segment, and the segments should be refreshed as hub behaviour changes. Tier stays useful as a model input (it ranks 2nd by F-score).

**Alert threshold and what it buys.** Threshold **0.5**. On the test set precision is 0.6889 — about **7 of every 10 flagged parcels are really delayed** — and recall is 0.7561 — about **7 to 8 of every 10 delayed parcels are caught** in advance.

**Today's batch.** Of the 48 new parcels, **8 are flagged**; **6** of those are in Escalate hubs and need a **hub-manager escalation** (HUB24, HUB18, HUB17, HUB20 and two at HUB21), and **2** get a **proactive customer call** (HUB22 and HUB09, both Watch). The other 40 need no action.

**Why K = 3.** The across-to-within distance ratio rises with K: 2.8940 (K=2, sizes 15-9), 5.3928 (K=3, 9-8-7), 6.3047 (K=4, 8-7-5-4), 6.8866 (K=5, 8-7-4-3-2). The jump from 2 to 3 is large, and K = 3 gives three balanced groups of 7–9 hubs. Beyond that the ratio keeps rising only because K-Means splits off tiny groups: K = 4 has clusters of 5 and 4 hubs and K = 5 has clusters of 4, 3 and 2 hubs — each below 6 hubs, too small to justify a playbook of its own. Operations runs exactly three playbooks, so K = 3 is kept.

## Production plan

**(a) Production-readiness characteristics mapped to this repository**

| Characteristic | Concrete item |
|---|---|
| Accuracy | Model choice from held-out validation and one test evaluation: `outputs/part_b_metrics.csv`, `outputs/part_c_final_test.csv` (test recall 0.7561, precision 0.6889). |
| Reliability | `outputs/part_d_reload_check.csv`: reloaded pickle gives the same probabilities as the in-memory model (max difference 0.0 over 180 test rows). |
| Reproducibility | Pinned versions in `requirements.txt`, fixed `random_state=42` everywhere, `generate_data.py` regenerates identical data; `predict_delay.py` output is byte-identical across runs. |
| Performance (speed) | `predict_delay.py` scores a batch with one `predict_proba` call on a pre-fitted pipeline (7 selected columns, 100 trees) — milliseconds per parcel batch, no retraining at scoring time. |
| Maintainability | Shared constants and logic in `src/shipment_prep.py`; final configuration lives in `outputs/part_c_final_config.csv`, read by `package_model.py`, not hard-coded. |
| Consistency | `predict_delay.py` calls the same `clean_shipments` and `build_features` as training, with the stored training medians (`models/impute_values.csv`) and the stored column order (`models/feature_order.csv`). |
| Monitorability | `delay_probability` and `flagged` are written for every parcel in `outputs/new_shipment_actions.csv`, so flag rate and, once outcomes arrive, precision/recall can be tracked. |

**(b) Quantities to monitor, with triggers**

1. **Weekly delayed share of delivered parcels** — training baseline 0.2317. Trigger investigation if a non-sale week is above 0.30 or below 0.15.
2. **Weekly share of parcels flagged** — on the 48-parcel batch it is 8/48 ≈ 0.17; on validation at threshold 0.5 it is 44/180 ≈ 0.24. Trigger if it moves outside 0.10–0.35 for two consecutive weeks.
3. **Recall on parcels whose outcome is now known** — target ≥ 0.80 (validation 0.8333, test 0.7561). Trigger a threshold review if the 4-week rolling recall falls below 0.70; trigger retraining if it stays below 0.70 after re-tuning the threshold.
4. **Precision on delivered parcels** — trigger review if the 4-week rolling value is below 0.55 (call-centre load becomes wasteful).
5. **Input drift** — mean `distance_km` per week outside 314.95 ± 50 km, or missing-value share in any raw input column above 5%.

**(c) Retraining and the sale window**

- **Schedule:** retrain monthly on a rolling window of delivered parcels (at least 3 months), plus an immediate retrain when a monitoring trigger fires. Re-run Parts A–D in order; re-cluster hubs quarterly, since segments change slowly.
- **Sale window (15–28 September, `sale_event_flag = 1`):** delays rise sharply during the sale (especially Express), so sale weeks must be compared against the **previous sale event**, not ordinary weeks — a jump in delayed share during the sale is expected and should not trigger drift alarms or retraining by itself. Keep sale-week rows in training so the model learns the effect, and track sale-week recall separately.
- **What drift would look like here:** new lanes pushing mean distance or stops up; a hub's delay rate moving it to another segment (as Kolkata or Nagpur already show versus their tier); a change in service mix (more Express); or a change in raw data quality (new spellings of `service_type`, more sentinel weights). Each shows up as a shift in input distributions, in the flag rate, or as falling recall on delivered parcels.

## Limitations

1. **Synthetic data.** All rows come from a generator with simple, mostly additive effects and Gaussian noise; real shipments have more complex patterns (traffic, hub outages, address quality), so real-world accuracy will likely be lower.
2. **Small evaluation sets.** The test set has only 41 delayed parcels and validation 42; one parcel moves recall by about 0.024, so the reported precision/recall are uncertain by several points.
3. **Threshold tuned on one split.** The 0.5 threshold and the choice of the untuned forest come from a single 180-row validation split; the three tuning candidates' F1 values (0.7750 / 0.7901 / 0.8333) are close enough that another split could reverse the choice. Test recall (0.7561) already fell below the 0.80 target.
4. **Only 90 days and one sale event.** Dispatches cover July–September 2026 with one sale window, so seasonality (festivals, monsoon peaks) is not represented.
5. **Hub segments from 50 parcels per hub.** Each hub's delay rate is estimated from 50 parcels (one parcel = 0.02 of delay rate), so borderline hubs may change segment with more data.
6. **Medians computed on the full history.** The fill-in medians use all 1,200 historical rows before the split; they carry no target information, but strictly a production pipeline would recompute them on training data only.
